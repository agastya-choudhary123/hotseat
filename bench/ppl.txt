The history of computing is often told as a history of machines, but it is at least as much a history of ideas about what a machine could be asked to do. Charles Babbage designed engines that were never built, and Ada Lovelace wrote about them as though they already existed, describing a device that could weave algebraic patterns the way a Jacquard loom wove flowers and leaves. A century later, Alan Turing replaced the machinery entirely with a description: a tape, a head, a table of rules. The point of the description was not to build anything, but to make it possible to prove that some questions have no mechanical answer at all.

When the first electronic computers arrived, they were understood as very fast arithmetic. Programming them meant rewiring them. The idea that a program could be stored in the same memory as the data it operated on took time to become obvious, and once it did, it changed what a computer was. A stored program can be modified. A stored program can be read by another program. Compilers, operating systems, and eventually everything that runs on a modern machine follow from that single structural decision.

Memory has always been the difficult part. Processors have grown faster far more quickly than memory has grown closer, and the gap between them is bridged by an elaborate hierarchy of caches, buffers, and predictions. A modern processor spends much of its time guessing: which branch will be taken, which address will be needed, which value will still be valid when it finally arrives. When the guesses are right, the machine appears to run at the speed of its arithmetic. When they are wrong, it runs at the speed of its memory, which is a different machine altogether.

Virtual memory is the oldest and most successful of these illusions. Each program is given the impression of a large, private, contiguous address space, and the hardware quietly translates every access into a location in physical memory, or into a fault that the operating system must handle. The fault is the interesting part. By choosing which accesses fault and what to do when they do, an operating system can page to disk, share pages between processes, copy pages lazily, or track exactly which pages a program has written since some moment in the past.

That last capability turns out to be the foundation of live migration. To move a running program from one machine to another without stopping it, you copy its memory while it continues to run, then copy again the pages it changed while you were copying, and again, until the remaining changes are small enough that you can afford to stop the program, send the last of them, and start it elsewhere. The program never learns that it moved. The only evidence is a brief pause, measured in microseconds, and the fact that the answer comes back from a different address.
